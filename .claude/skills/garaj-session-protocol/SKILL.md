# Протокол сессии GARAJ.KG

## Почему это критично

Каждая сессия Claude начинается с чистого клона. Всё, что не закоммичено и не
запушено, — ПОТЕРЯНО навсегда. Вся память проекта живёт в одном месте:
`CLAUDE.md` (шапка: «шпаргалка проекта — читается автоматически в каждой
сессии»). Основатель (djaha) — соло, не технический, по-русски; он не сможет
восстановить контекст за тебя. Поэтому протокол ниже — не бюрократия, а
единственный механизм преемственности между сессиями.

## 1. Ветки и коммиты

- Работай ТОЛЬКО на ветке `claude/*` (примеры из истории:
  `claude/garaj-kg-continuation-oyn7az`, `claude/bakai-acquiring-login-937595`).
  Прод деплоится Vercel'ом автоматически с `main` — любой push в `main`
  мгновенно уходит живым пользователям.
- Коммиты — ПО-РУССКИ, в стиле истории (`git log --oneline`; примеры:
  «Мерж: /app — айфон первым…», «Память: правило "поставщиков не светить…"»).
- Цикл выката (закреплён в CLAUDE.md): работа на `claude/*` →
  `merge --no-ff` в `main` → push `main` → авто-деплой Vercel →
  `post-deploy-check` (probe-prod + probe-sell, `.github/workflows/`).
- `--no-ff` обязателен: мерж-коммит («Мерж: …») — это единица журнала, его SHA
  пишется в CLAUDE.md как метка «что в проде».
- Перед мержем ОБЯЗАТЕЛЬНО `git fetch` и разбор чужих коммитов на `main`:
  параллельные сессии — реальность (11.07 две сессии одновременно правили
  удаление аккаунта; конфликт пришлось разруливать вручную).

## 2. Мерж в main — ТОЛЬКО по явному слову основателя

⛔ НЕ мержить в `main`, НЕ менять видимое поведение, НЕ трогать боевые данные
без ЯВНОГО «да» (правило из раздела «Стиль работы с основателем» в CLAUDE.md).
Почему: в проде живые пользователи и живые деньги; основатель — единственный,
кто решает, что видят люди.

Что считается словом на мерж (реальные формы из журнала):
- «мержи», «Мержи», «мержи все», «да»;
- условное: «если не будет багов — мержи» → сначала прогнать аудит/проверки,
  мержить только если багов реально нет;
- с оговоркой: «мержи, но для айфона только в TestFlight» — выполнять буквально;
- стоячее разрешение: «потом можешь мержить» — действует, пока не отозвано.
Что НЕ считается: молчание, «ок», похвала, твоя уверенность в качестве.
Прямые запреты фиксируй и соблюдай (пример из истории: «платёжное пока не
мержи», 06.07.2026 — платёжная ветка ждала слова и была влита в main 07.07.2026).

Пока слова нет — работа живёт на ветке со статусом «ЖДЁТ МЕРЖА» в журнале.
Просьба основателя «Покажи перед мержем» — норма: показать скрины/стенд,
ждать решения.

Перед тем как просить мерж, ВСЕ проверки зелёные:
`cd web && npm run lint`, `tsc`, тесты, `npm run build`. Перед `npm run build` —
убей живой next-server (`pkill -f next-server`); остальные капканы сборки —
skill garaj-known-traps. В журнал пишется
формулой: «tsc/eslint/227 тестов/build зелёные» (число тестов — актуальное).
После мержа проследить CI (`ci.yml`) и смоуки `post-deploy-check.yml`.

## 3. Конец сессии — три обязательных шага

1. **Закоммитить и запушить ВСЁ** (ветку; `main` — только если было слово).
   Из CLAUDE.md: «В конце — закоммитить и запушить (иначе следующая сессия
   не увидит)».
2. **Дописать журнальный блок в `CLAUDE.md`** — датированный, СВЕРХУ,
   сразу под H1 `# CLAUDE.md — шпаргалка проекта…` (порядок newest-first,
   так следующая сессия первым делом читает самое свежее).
3. **Запушить сам CLAUDE.md** — журнал без пуша не существует.

## 4. Шаблон журнального блока (выведен из реальных записей)

```markdown
## DD.MM.YYYY — ЗАГОЛОВОК СУТИ СЕССИИ (В ПРОДЕ, мерж <sha> по «мержи», ci+смоуки зелёные)
ТЗ основателя («точная цитата его слов»): что просил, как понял.
Что сделано и КАК (файлы, компоненты, флаги):
- **Главное изменение** — суть, путь к файлу, ключевое решение.
- **Второе изменение** — …
Проверки: tsc/eslint/<N> тестов/build зелёные; <что проверено живьём>.
⚠️ КАПКАН: <грабли, на которые наступил — чтобы следующая сессия не наступила>.
⚠️ ПРАВИЛО: <новое постоянное правило, если родилось>.
⛔ <решение основателя: что отклонено/запрещено — с его цитатой; не возвращать>.
Открытые хвосты: <что не доделано, что ждёт решения/проверки основателя>.
```

Варианты статуса в скобках заголовка (все — из реального журнала):
- `(В ПРОДЕ, мерж <sha>, ci+смоуки зелёные)` — смержено и задеплоено;
- `(В ПРОДЕ, мерж по «мержи»)` / `(мерж по «мержи все»)` — фиксируй, каким
  именно словом дан мерж;
- `(ЖДЁТ МЕРЖА, ветка <branch>)` / `(ветка oyn7az, аудит SAFE, ждёт мержа)` —
  сделано, но слова не было;
- серия мержей: `(ВСЁ В ПРОДЕ, мержи cdc61a1→998f6a7→…, все CI/смоуки зелёные)`.

Правила содержимого блока:
- Цитируй основателя ДОСЛОВНО («ужасный вариант, отмена, оставим как есть») —
  цитата = доказательство решения, следующая сессия не сможет его «переиграть».
- Отвергнутые итерации перечисляй явно с пометкой «ОТВЕРГНУТЫ, не возвращать».
- ⚠️ КАПКАН — для технических ловушек (пример из журнала: next/image кэширует
  варианты в `.next/cache/images` — заменённый PNG под тем же именем покажет
  старую картинку, поэтому новые арты — под новыми именами).
- ⚠️ ПРАВИЛО — для постоянных запретов (пример: «лента категорий в SellWizard —
  БЕЗ scroll-snap… snap-x НЕ возвращать»).
- Подблоки той же сессии — `###` под основным `##` (пример: «### ВЕЧЕР
  10.07.2026 — доводка…»).
- НИКОГДА не вставляй в журнал секреты/токены/ключи — только ИМЕНА env-переменных
  (в журнале уже был инцидент «токен светился на скрине → пересоздать»).

## 5. ⛔-решения и спящие флаги — не трогать

- Всё, что в CLAUDE.md помечено ⛔ или «ОТКЛОНЕНО ОСНОВАТЕЛЕМ» /
  «ОТВЕРГНУТЫ, не возвращать», — НЕ предлагать заново и не возвращать в код.
  Основатель уже потратил время на это решение; повторное предложение = ты не
  читал память. Примеры: 3D-арт вместо фото в hero («ужасный вариант, отмена»),
  дневной крон автожурнала (отключён 30.06 — «дорого»), архивные доки
  `STRATEGY.md`/`INTEGRATION-CARCHECK.md`/`BANK-ONEPAGER.md`.
- `web/lib/flags.ts` — кладбище выключенных фич (SHOW_SCORE, SHOW_VERIFICATION,
  SHOW_INSPECTION, SHOW_OSAGO, SHOW_VIN_CHECK, SHOW_AI_ANALYSIS, SHOW_FINES,
  SHOW_FAIR_PRICE и др.). Комментарий в самом файле: «выключено решением
  основателя… Включать только с его явного разрешения». Код за флагами НЕ
  удалять, но и за готовое/имеющееся НЕ выдавать; НЕ включать ни один флаг,
  пока основатель сам не попросит.
- То же для функций «заложено, но не подключено» (доп-тарифы за
  `SHOW_EXTRA_PROMOS`, цены из `web/lib/promo-prices.ts` — «цены/линейку без
  банка не менять»).

## 6. Как говорить с основателем

- Только по-русски, по делу, без воды. Он часто пишет голосом→текст: опечатки
  и обрывки — норма, понимай по смыслу, при реальной двусмысленности —
  переспроси.
- Он не технический: операционные шаги (Vercel/Google/банк/App Store) —
  разжёвывать «пальцем», по клику: куда зайти, что нажать, что увидит.
  Жаргон (rebase, ISR, edge-кэш) — не употреблять; код — делать самому,
  деталями не грузить.
- Перед необратимым (сброс данных, деплой, миграция) — показать сухой
  прогон/план и получить подтверждение.
- Большие правки — через агентов + аудит кода/безопасности, сборка зелёная;
  предложения, меняющие видимое поведение, помечать «ЖДЁТ "да"» и не делать
  самовольно.

## 7. Чек-лист перед завершением (прогнать всегда)

1. Работа на `claude/*`? Коммиты по-русски?
2. Мерж в `main` был ТОЛЬКО по явному слову (и слово процитировано в журнале)?
3. `git fetch` + разбор чужих коммитов перед мержем сделан? Мерж `--no-ff`?
4. lint/tsc/тесты/build зелёные, статус записан формулой?
5. Журнальный блок добавлен СВЕРХУ под H1 в `CLAUDE.md` (дата, статус, ТЗ,
   капканы, ⛔-решения, хвосты)?
6. ВСЁ закоммичено и запушено (включая CLAUDE.md)?
